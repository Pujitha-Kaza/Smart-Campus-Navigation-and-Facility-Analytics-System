DEPARTMENT TREE DESIGN (MEMBER C)

The DepartmentTree module uses a general tree rather than a binary tree. Each
DepartmentNode stores the department's original spelling, a non-owning pointer
to its parent, and a vector of unique_ptr children. The vector allows any number
of children and preserves sibling insertion order. unique_ptr gives the tree
clear ownership and recursively releases all nodes when the tree is cleared or
destroyed.

Department names are trimmed and compared case-insensitively, while the spelling
from the first accepted record is preserved for display. Searches use a recursive
depth-first scan of the tree. The parent pointer provides the parent name and
allows depth to be calculated by walking from a found node to the root.

File loading reads complete lines with getline, skips blank and comment lines,
splits each record on the pipe character, and validates field count, empty fields,
duplicate names, the root's NONE parent, and previously accepted parent names.
Invalid records produce a warning and do not modify the tree. The hierarchy and
the traversal both use preorder; the hierarchy adds four spaces per depth while
the traversal prints a single unindented sequence.

FACILITY DATABASE AND HASH TABLE DESIGN (MEMBER A)

The Facility module is split into include/Facility.h for the record and load
result, include/FacilityHashTable.h and src/FacilityHashTable.cpp for the ID
index, and include/FacilityDatabase.h and src/FacilityDatabase.cpp for loading,
validation, display, and search. FacilityDatabase::loadFromFile accepts the
accepted building names as a const vector<string>& so the shared loader can pass
the spellings read from buildings.txt. Facilities are retained in a vector in
accepted file order; the index holds facility values in its own buckets.

The custom hash table starts with 11 buckets. It uses separate chaining, with
each bucket stored as a dynamically growing vector. Separate chaining was
selected because the table can accept any number of facilities without a full
table condition or an arbitrary facility limit. The hash formula processes each
byte of the normalized uppercase ID in order: h starts at zero, then for each
character c, h = (h * 31 + unsigned ASCII value of c) % capacity. Lookup hashes
the normalized ID and checks only entries in that bucket; it never scans the
facility display vector.

A collision is counted when a unique, accepted key is inserted into a bucket
that is already nonempty. Duplicate keys are detected before insertion and do
not increment the collision count. Duplicate facility IDs compare after
uppercasing, so the first accepted record remains stored; repeated facility
names are allowed. Since buckets grow dynamically, insertion never fails due
to a full table.
